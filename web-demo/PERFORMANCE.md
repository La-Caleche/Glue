# JCEF measurements and interpretation

These are exploratory in-game samples on Windows 11 / i9-10900K / RTX 4080 SUPER, JCEF
146.0.10.1. The CEF cap is 60 FPS unless specified. They are not interleaved statistical benchmarks
or direct measurements against a running Graphene build.

## Local React fixture

The small local fixture ran at approximately 60 callback FPS and 59–60 upload FPS. In one sampled
window (854×372 browser pixels, CSS animation running):

| Mode | Capture | Stage | CPU conversion | Upload | Probe to paint | Probe to upload |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GPU BGRA | 0.329 ms | 0.132 ms | 0 | 0.243 ms | 16.8 ms | 25.3 ms |
| CPU RGBA | 0.330 ms | 0.124 ms | 0.181 ms | 0.133 ms | 17.2 ms | 24.8 ms |

About 72% of the surface was damaged during these samples. The CPU conversion cost is visible,
but this sample does **not** establish a significant end-to-end advantage for GPU channel swapping.
It also does not isolate the cost of the full historical Graphene presentation/input stack.

## La Calèche

Visual inspection confirmed the gradient heading and soft background effects absent from the
Obscura capture. The native-resolution screenshot is generated by `glue-test:jcef-sites`.

The first large-surface run at 2560×1178 delivered about 60 CEF callbacks/s but 47 uploads/s, with a
291 ms paint probe and 298 ms upload probe. This slow sample is retained here rather than discarded.

A subsequent run added a JS acknowledgement and a 30 FPS pacing comparison:

| Surface / cap | CEF FPS | Upload FPS | Capture | Stage | Upload | JS ack | Probe paint | Probe upload |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 854×292 / 60 | 59.6 | 59.6 | 0.268 ms | 0.114 ms | 0.084 ms | 3.2 ms | 35.7 ms | 43.9 ms |
| 2560×1178 / 60 | 59.4 | 59.4 | 3.401 ms | 1.425 ms | 1.234 ms | 0.7 ms | 40.0 ms | 44.4 ms |
| 2560×1178 / 30 | 29.8 | 29.8 | 3.520 ms | 1.459 ms | 1.171 ms | 6.1 ms | 64.6 ms | 70.3 ms |

The large page damages almost the whole surface each frame. A 30 FPS cap reduces the frequency of
copies/uploads but increased the sampled round-trip latency. It remains a manual tradeoff, not an
automatic optimization. The low acknowledgement time in the 60 FPS sample locates most of that
probe's delay after the JavaScript round trip, but cannot distinguish every Chromium compositor,
raster, readback and scheduling stage.

## What this establishes

- A small direct JCEF integration can provide full browser rendering with native inputs and smooth
  delivery in these fixtures. Java-side DOM/input emulation is unnecessary.
- Damage accumulation across skipped frames is essential for correctness. Reusing only the last
  callback's dirty rectangles would lose changes made in earlier unconsumed frames.
- Large surfaces still cost several milliseconds of CPU copying/upload submission. Native frame
  delivery and latency can vary substantially even with this small wrapper.
- Renderer naming is not a GPU-sharing guarantee: both tested paths receive CPU `onPaint` buffers.
  The shader avoids channel conversion, not CEF's upstream buffer/readback path.

## Next useful experiments

1. Compare the exact historical Graphene artifact with this host using the same CEF build, page,
   viewport, profile, frame cap and render load. The backport source used 146.0.10.1, but an older
   143.x native installation also existed in the Graphene run folder; the previous runtime is not
   conclusively identified.
2. Gather latency distributions from many correlated probes instead of individual samples. Keep
   warmup, navigation, typing, animation and idle measurements separate.
3. Profile Chromium/readback and callback scheduling when slow probes recur. A good upload time
   does not prove that the whole browser-to-game path is fast.
4. Evaluate shared-texture `onAcceleratedPaint` only if CPU transport dominates. This requires
   platform-specific interop and explicit resource/synchronization ownership; it is a separate
   experiment from the current BGRA fragment shader.

Native memory/RSS, low-end hardware, active shaderpacks, multimedia playback and physical
input-to-photon latency were not measured. No blanket claim of being faster than Graphene or JCEF
in general follows from these initial observations.

## Subsequent manual feedback

On 2026-09-14, the maintainer reported smooth 1080p YouTube playback with no perceived audio delay or
frame drops. The 30 FPS web cap was considered fluid and usable, with a small perceptible delay when
scrolling. The missing native cursor shapes were the principal remaining issue reported. These are
manual observations, not measured playback statistics or a cross-hardware comparison.
